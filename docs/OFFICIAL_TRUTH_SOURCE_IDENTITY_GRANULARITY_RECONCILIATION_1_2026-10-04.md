## 1. Decision

**Select Option A. `sourceId` remains the authority/publisher domain-trust identity. Add a mandatory, server-owned `contentItemId` and a separate representation identity. Composition distinctness becomes distinct `(sourceId, contentItemId)` pairs.**

A National List item and an Appendix item may share the same authority and host. HTML and Content API renderings of one item share its support identity even when their bytes, URLs and Evidence versions differ. Domain permission is necessary for retrieval; it never suffices to approve a publication.

This decision is a future contract, not implemented behavior. It supersedes the content-item-as-`sourceId` statements in composition architecture sections 3, 4.3, 6 and 8, especially the sentence at line 351 of `OFFICIAL_TRUTH_COMPOSITION_PROVENANCE_POLICY_ARCHITECTURE_1_2026-10-03.md`. It also supersedes the proposed content-specific source naming pattern in CTA audit section 6. The CTA one-item membership proof survives; its provenance type needs the item binding defined here. No historical document or global current-state file is edited by this task.

| Option | Decision and reason |
| --- | --- |
| A: authority `sourceId`, separate content item | Selected. Preserves existing domain ownership, official/provider classification, overlap checks and source references. Changes the overloaded support selectors explicitly. |
| B: content-item `sourceId`, separate authority | Rejected. Still needs an authority table/identifier, changes every current meaning of `sourceId`, and replaces domain resolution and source foreign keys while also needing representation and Evidence changes. It has no compensating reduction in work or risk. |
| C: URL/path/hash is the support id | Rejected. A second rendering or moved path becomes a false second support; a reused path becomes false continuity; identical bytes merge different publishers. A path-prefix exception to the domain model also creates ambiguity. None is smaller while satisfying the invariants. |

## 3. Six identities and their owners

All names below are proposed contract names. No actual GOV.UK Jetnity identifier is allocated here.

| Identity | Canonical meaning / owner / equality |
| --- | --- |
| Authority/domain | Existing `sourceId`: one reviewed official publisher trust boundary, its class, authority/publisher metadata and permitted domains. Server catalog registration only. An official publishing platform can be this boundary; it is not an assertion that every page has the same competent department. Item-level publisher expectations preserve that distinction. Licensed providers retain their separate class and cannot supply official-primary support. |
| Content item | `ContentItemRef = {sourceId, contentItemId}`. Immutable authority-scoped id for one reviewed publication. Both ids use the existing bounded lowercase id grammar; the ordered pair is the identity. Publisher `content_id` is an expected external identifier under a pinned namespace, not the Jetnity id or a capability. |
| Representation | `RepresentationRef = {sourceId, contentItemId, representationId}` plus positive `representationVersion`. The id denotes one rendering stream (format/locale), not a particular download. Each immutable descriptor version pins exact request/final URLs, media type, identity-verifier id/version and expected metadata. Bytes and retrieval time belong to the observation/Evidence, not to this reusable id. |
| Evidence version | An immutable `ev2_` value for the exact bound representation observation and one regulatory cell. It includes the item and representation identity, descriptor version, full-source fingerprint, final URL, retrieval time, validity and scope. It is neither the item id nor a support count. |
| Composition support | Exactly `ContentItemRef`. No independently mintable support id or support table. A request maps each distinct pair to exactly one accepted Evidence version. Another representation/version of the same pair cannot be an additional support. |
| Runtime provenance | Versioned deterministic execution identity over ordered bindings of item, representation, Evidence, verifier, scope/review identity, extractor/policy versions and citation targets. It explains an execution; a string/hash/JSON record never authorizes it. The ephemeral execution seal remains non-JSON. Persistence/retention needs its own gate. |

Use canonical tuple serialization, never ambiguous concatenation of free-form ids. Sort support pairs lexicographically by sourceId then contentItemId. Reject duplicates rather than removing them and continuing.

### 3.1 Content registry and identity verification

One server-owned content registry is subordinate to `QuellenRegistry`; it does not duplicate domain rules. A `RegistrierterInhaltsgegenstand` has its immutable pair, external-id namespace/value, current immutable identity descriptor version, and expected competent publisher metadata. Identity descriptors are append-only, carry `current`, and have at most one current version per item. A representation descriptor belongs to exactly one such item descriptor version. A profile change cannot silently mutate old Evidence.

Registration is an explicitly reviewed server administrative operation, never a research/model request. Source registration creates no content permission. Item registration requires an existing source, a unique `(sourceId, externalIdNamespace, externalContentId)` and reviewed proof that the listed representations are renderings of this item. One external item cannot get two Jetnity ids to inflate support count. For a publisher without a stable external item id, namespace `jetnity-reviewed-item` and an opaque server-allocated review key explicitly identify that absence; they must never be presented as publisher metadata. Such an item requires an exact full-content fingerprint identity profile, and changes require review. It gets no automatic path-move continuity. Registration must reject a second item for an already reviewed same-item rendering even when no external-id uniqueness constraint can prove that equivalence by itself.

Representation descriptor versions contain a finite list of exact normalized request URLs, exactly one expected final URL, one expected normalized response media type, exact locale/schema/publisher expectations, and an identity profile id/version. A descriptor revision cannot change its item pair or external-id identity. A change of rendering format or locale starts a new representationId, not a new item; a replacement external item starts a new contentItemId. URLs are admitted only after the existing authority/SSRF checks. There are no path-prefix, regex-path, wildcard-query or host-only content grants. Query-bearing URLs must match exactly; no parameter reordering or removal creates equivalence. Fragments are removed before request identity using the existing rule. No arbitrary subpath inherits approval.

Load validates all active descriptors as one set. One canonical URL may resolve to exactly one current item/representation descriptor. Duplicate or overlapping active bindings fail the catalog load, including ambiguous bindings inside the same item. Historical descriptor URLs remain reserved to that item; a reused URL for another item requires an explicit reviewed retire-and-rebind transition, invalidating the former current binding. Historical provenance is retained, not rewritten. A URL resolving to zero items fails content eligibility. Enumeration order is never a tie-break.

The code-owned **identity verifier** is separate from the legal-fact extractor. It takes the frozen expected descriptor plus the server's response bytes, final URL and observed media type; returns only an identity verdict/bound tuple, never a legal effect. Production verifier profiles remain empty until separately reviewed. A registry row names an existing code profile; it cannot supply executable selectors, code or a user-defined extraction expression.

For a future structured publisher profile, require an unambiguous root object, duplicate-key rejection, exact external content id, base path, schema/document type, locale, live/withdrawn state and publisher identifiers. Inspect the designated root identity fields, not a regex hit anywhere in the body or in linked-item metadata. HTML needs a reviewed equivalent profile authenticating that rendering's own item metadata; an id merely mentioned in text is insufficient. If that cannot be proved, the representation stays ineligible. A known Content API relationship does not automatically authenticate arbitrary HTML bytes. Exact-content profiles bind the entire response fingerprint and never auto-learn a replacement hash.

These profiles establish **which official item was fetched**, not whether its legal statements are complete or true for a traveller. A server-derived hash proves byte/text equality only after the transport and item checks. Neither model-parsed metadata nor a caller assertion can replace those checks.

## 5. Evidence identity and deterministic continuity

`EvidenceVersion.sourceId` retains authority meaning. V2 additionally requires `identitySchema: 2`, `contentItemId`, `contentItemVersion`, `representationId`, `representationVersion`, `identityVerifierId`, `identityVerifierVersion`, and observed `contentType`. The corresponding item/representation fields are part of Evidence identity, with identical copies checked wherever projected into scope or proof. Descriptor versions are resolved server-side. No nullable/default item derived from hostname, title, first path, hash or sourceId.

The canonical Evidence lookup changes once to **`evidence-key:v3:`**. Its canonical JSON is the existing v2 regulatory cell serialization, with `v: 3`, authority sourceId, contentItemId and representationId. Keep all current regulatory dimensions, sorted citizenships and explicit credential relation; no parallel scope parser. Descriptor versions and URL are deliberately excluded from the lookup stream: a reviewed path move within the same representation can retain stream identity. HTML and API have different lookup streams, even though their support identity is equal. `rule-scope:v1:` remains source/item/representation-neutral; `regelScopeAusEvidenceScope` projects the same regulatory cell.

The new **`ev2_` + 32 hex** id is the truncated SHA-256 of a fixed-order canonical JSON object with `identitySchema: 2`, sourceId, contentItemId, contentItemVersion, representationId, representationVersion, identityVerifierId/version, lookupKey, canonicalUrl, contentType, sourceContentHash, retrievedAt, validFrom and validUntil. Validate every component before serialization. This also prevents a validity-window change reusing the same version id. Keep extractionNote, lifecycle and previousVersionId outside the version hash; they are annotation/state/lineage, not a different observation. A version-id collision with different full identity is a conflict, never an overwrite.

`sourceContentHash` keeps `evidenceQuellenFingerprint`'s existing SHA-256 of line-ending-normalized complete source text. It is **not generally raw-byte SHA-256**. Retrieval still bounds raw bytes, uses fatal UTF-8, and recomputes the fingerprint; no substring, parsed JSON, pretty print, model summary or legal-fragment hash substitutes. If later retention requires raw-byte digests, introduce a separately named field in that separate scope; do not silently change this hash contract. Binary PDFs remain ineligible under the current UTF-8 transport unless a separate reviewed retrieval extension supports them.

`evidenceKandidatAusModell` must reject model authority/item/representation/verifier overrides. Trusted identity comes from the server-resolved material envelope, even where a model proposes scope. `evidenceKandidatAkzeptieren` and `akzeptierteEvidenceLesen` revalidate descriptor membership, source metadata, scope equality, lookup and the recomputed version id. The reader is still structural; it must never be described as live HTTP proof. The server-owned acceptance/store path additionally verifies item identity from fresh retrieval before writing v2 Evidence.

Ordinary refresh requires the same authority, item, representation, descriptor versions, exact final URL, semantic source metadata and regulatory cell before comparing fingerprints. Changed content returns changed content and `ruleChange: not_asserted`; it is not automatic Rule acceptance. A changed content id, publisher, profile or URL is identity drift even if bytes hash equally.

An item that moves is **blocked by ordinary refresh**. A separately reviewed new descriptor may pin the same independently authenticated external item id at its new exact URL; retire the former current descriptor and explicitly re-prove the new representation. Create a new Evidence version; never rewrite canonicalUrl on the old version. A path serving a replacement id cannot inherit the old item. A changed authority sourceId creates a new pair, with any historical relation informational only. A publisher metadata change under the same platform requires explicit item-descriptor review; it is not automatically a new legal support.

`previousVersionId` is optional historical linkage only. Require an existing version with the same source/item/representation/lookup stream, no cycle, and chronological predecessor. A reviewed descriptor transition may cross descriptor versions inside that stream after independent reproof. It cannot bridge HTML to API, a replacement item, another authority or another regulatory cell. It cannot authorize a new version. No implicit previous-chain backfill exists for `ev1_` records.

## 6. Same-request proof, retrieval and extraction

The server flow becomes:

1. Reject caller authority/proof/catalog/item-definition fields and verify the existing role capability. Caller/model/plugin content-id assertions cannot mint, override or select registered identity. An existing proposed sourceId/URL remains only a lookup hint.
2. Read one v2 catalog snapshot; validate/freeze authorities, denies, items, representations and profile pins together. Resolve every proposed exact URL and source hint to one registered tuple. Rebuild accepted Evidence/candidate/review identity with v2 semantics. This binds expectations; submitted research bytes still do not prove current origin.
3. Each proof support contains versionId, sourceId, contentItemId/version, representationId/version, verifier id/version, exact canonical URL, observed Evidence content type, sourceContentHash, retrieval time and validity, bound to the same ruleScopeKey. Require one accepted version per support pair. Freeze the full support-to-version bijection.
4. Before any HTTP, select one current extractor and, for composed quality, one policy from the item-aware proof and code-owned definitions. Freeze their exact ids/versions and representation eligibility. No content type or response schema chooses between candidates.
5. Replay only that snapshot to retrieval. It is an internal server transport, not caller input. Preserve all deny/item/representation fields. No second external catalog read, live-row lookup or response-driven registration is permitted.
6. Retrieval internally carries the exact expected tuple and descriptor versions selected from the snapshot. The public entry still accepts only the established sourceId/URL proposals, deriving the tuple itself. Reject any injected contentItemId, representationId, expected metadata or verifier claim at that public boundary. The trusted same-request seam receives the already server-resolved tuple and checks it against replay.
7. Apply current HTTPS/default-443/no-credentials/tracking/blocked-domain protections before the initial connection and every redirect. Preserve connection-bound DNS/IP filtering, TLS validation, private/loopback/link-local/range blocks, at most five redirects, loop detection, 10-second bound and 65,536 raw bytes. A content binding can only narrow these protections.
8. Redirects must follow the descriptor's finite reviewed request-to-final URL chain, retaining the same source, item and representation. Different item on the same host fails before the next socket. A second approved host passes only if it resolves to the same source and explicitly belongs to that same descriptor's approved chain; another source fails `redirect_source_mismatch`. Default descriptor redirect allowance is zero. A new path is never learned from `Location`.
9. After the bounded response arrives, verify final URL, observed media type and the response's own item metadata through the pinned identity verifier **before the legal matcher/extractor runs**. Unavailable, missing, ambiguous, wrong or withdrawn item metadata blocks. Return a frozen server-owned retrieval binding; an arbitrary structurally equal object is not a substitute for the live entry.
10. Rebind source/item/representation/descriptor/verifier tuple, exact accepted Evidence final URL/type/fingerprint/version/scope, both before and after the existing extractor execution seam. Fresh retrievedAt is a new observation time, not required to equal the historical Evidence time. A fresh hash change blocks extraction against that Evidence; do not switch versions or renderings inside the request.
11. Produce immutable fact/provenance or the existing composed execution seal only after identity, parsing, observations and citation checks. No Rule acceptance or persistence is implied. F7 remains its current narrow non-bearer projection; item fields live on the internal graph, not an enlarged public witness.

New internal failures should distinguish `content_item_unregistered`, `content_item_mismatch`, `representation_mismatch`, `identity_profile_unavailable` and `content_identity_drift`. Existing source/SSRF failures retain their meanings. None becomes `not_required`. Low-level pure/test constructors and injected transports remain test seams, never new route authority.

## 7. Extractor and composition policy contracts

Replace support selector/assignment fields named `sourceIds` with **`contentItems: readonly ContentItemRef[]`** wherever they currently mean composition participants. Do not change the meaning of sourceId itself. A derived unique authority `sourceIds` list may remain informational in results, but cannot select policy, count supports or assign a field. Strict parsers reject legacy source-only selectors at the new boundary; no one-item-per-authority fallback.

### 7.1 Extractors

`OfficialTruthExtractorDefinition.contentItems` is an exact sorted set, one item for explicit-primary or 2–8 items for composed quality. Each definition also pins the permitted representation descriptors **per item**. Keep `sourceFamilyId` as a code-owned name for this reviewed extraction family, not a publisher, hostname or inferred content id. Schema family remains code-owned. URL allowlists remain an additional narrowing constraint, not a union that lets an Appendix URL impersonate the National List support.

At most one current extractor per `(factKind, contentItems)` exists. Definitions differing only in representation, URL, observed type or schema cannot become competing current entries for that key. Support multiple eligible renderings inside the one versioned definition with explicit per-representation parser branches; select the branch from the proven representation binding before parsing. If a new rendering is not supported by that definition, fail rather than choosing another extractor after HTTP. Content-type checks verify the frozen branch. Definition changes allocate a new extractor version.

`stuetzeBinden` validates the full tuple and recomputed source fingerprint, not just sourceId. `OfficialTruthExtractorStuetze`, context and output provenance carry the item and representation. Mandatory composed observations become `{targetKey, contentItem: ContentItemRef, canonical}`; each observation must resolve to the unique freshly bound version for that item. No caller observation list, source-only observation or first support for a host is accepted. Keep the single `definitionAusfuehren` pipeline and canonical `regelFaktLesen`; the policy module must not introduce another parser/execution path.

### 7.2 Composition

The pre-HTTP key is exactly `(factKind, requirementType, sorted contentItems, sourceFamilyId, schemaFamily)`. Family/schema names come from the selected code definition, not the request. Applicability schema and observed content type remain verification pins, not selectors. Registry load rejects duplicate keys and duplicate current extractor matches. Runtime zero/multiple matches fail before HTTP. Phase B verifies the frozen pair without re-selection.

An assignment has its existing citation target, relation and role, plus a nonempty `contentItems` subset. `single_source` is retained as the legacy relation tag meaning exactly **one content item**, and `equal_values` requires at least two distinct items with complete equal observations. Document the legacy tag; do not count authorities under it. Targets, support-free structural atom locators, tie-group bijections and completeness `joint_complete_fact` remain unchanged.

Replace every map `sourceId -> versionId` with `ContentItemRef -> exactly one versionId`. Every branch/atom/outcome/otherwise projection uses this map. Preserve complete branch unions, atom-within-branch constraints, assignment coverage, missing-observation failure, duplicate-value failure and conflicting-value failure. Two items under one authority must retain two independent observation rows; deduplication by authority would erase one and is forbidden.

For the new identity contract, replace failure `same_source_composition` with **`same_content_item_composition`** when fewer than two distinct items are offered. Preserve `ambiguous_structure` for a repeated item inside a larger support set or multiple versions/representations for one item. No dedupe-and-continue. Historical v1 results keep their old diagnostic text. Pure Rule acceptance adopts the same distinct-item and one-version-per-item invariant when its own separately dispatched identity wiring lands.

Provenance rows contain citation target/key, sourceId, contentItemId/version, representationId/version, versionId, verifier id/version and extractor/policy ids/versions. Include all these bindings in a versioned `officialTruthCompositionProvenanceIdentity`; do not take extractor identity blindly from one arbitrary row. Validate consistent execution identity across rows and sort rows by citation key then item tuple/version before serialization. Policy revisions are required for changed item assignments even where the authority set stays unchanged.

Distinct identity does not prove legal independence or completeness. Two authorities with identical bytes remain two identities; equal bytes neither merge them nor grant composed quality. The code-owned policy still has to justify their respective complete roles. Republishing/copying must not be treated as independent corroboration merely because two item ids exist. One authority's documented mirror of the same external item remains one content item with multiple representations.

## 8. Rule Claims and CTA pin

`regelKandidatAkzeptieren` remains the sole canonical Rule acceptance constructor.
